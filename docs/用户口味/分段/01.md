## 评判与验收方式（TA 怎么看界面、怎么判定好坏、要 AI 怎么证明）

- 先看截图再说话，常常只发一张图，或者「你对比看看」，让 AI 把产出和参考图并排比：「[Image #10] 你对比看看。」「你觉得好看吗？我觉得很差劲。」（03-31 · new-bitable-poster-generator）；目标是和参考图一模一样：「你再生成一批，多个agent并行检查。[Image #5] 直到你们生成的图片可以跟我的示例图一模一样为止。」（04-18 · 批量排版插件）。
- 在真实环境走一遍：复制到公众号编辑器、在 Windows 上打开拆分文件、手机打开 PDF，以真实结果为准，不以本地预览为准（「这个问题我已经提了10多次了，你只有某一次是解决的」04-03 · fbif-wechat-layout）。
- 每个按钮都要和后台真打通：「好好把执行台的每个功能、每个按钮、每个交互、每个页面，都好好检查一遍，我发现很多功能实际没有用。而且他无法真正与后台打通。」（04-16 · 企业微信智能客服）。
- 用会变的数据测：「主要是你要做好测试，多个agent，可以先弄一份模拟数据」（04-16 · 议程生成），比如嘉宾改名、话题变长、嘉宾一下变多。
- 让多个角色化 agent 挑刺、最后一人拍板，再交给 codex 审：「评价这个页面的前端，有的是强迫症，有的是设计师，有的是乔布斯。有的是产品经理。然后最终有一个CEO，负责收集给出决策」（04-08 · 企业微信智能客服）；「你现在弄5个agent，给我盯着看，你看看问题出在哪里？」（04-16）；「也要有审核的agent驻场把最后一道关。」（04-18 · 批量排版插件）。
- 判断标准的说法：「不符合直觉」（03-27 · mote-research）、「你要符合操作直觉」（04-02 · 模板编辑器）、「需要兼顾好看和实用。」（04-10 · 企业微信智能客服）、「我是一个强迫症」（04-16）、要有「乔布斯这样的产品眼光和对细节的绝对追求」（04-16）。
- 以使用者身份判断：「因为你面对的是客户。」（03-23 · fbif-wiki）；「因为一线业务人员他们不知道什么是ID。」（03-27）；「你面对的都是高级客户，都是企业的总裁级别的，所以这个PDF模版要足够高级。」（04-16 · 企业微信智能客服）。

## 和 AI 合作做界面的方式（回复长短、问不问、先给什么、怎么改）

- 动手前先出方案 / 设计规范 / 样式稿给 TA 确认，确认后再改；改完再让 TA 确认（反复 9 次）：「可以先给我看看你的设计规范」（03-27 · mote-research）；「改完之后跟我确认一下。」（03-27）；「确认好方案后再执行。先跟我确认。」（04-02 · fbif-wechat-layout）；「先确认一个修改计划给我」（04-07 · FBIF公众号排版）；「3. 跟我确认一下方案后再继续实现」（04-11 · 发送监控）；「你可以先跟我确认一下你的架构和思路。」（04-13 · 群发名单整理助手）；「然后你需要先设计一下样式给我。」（04-16）；排查时「先不改，先记录」「先别改，看看怎么搞的」（04-17 · 企业微信智能客服）。
- 设计先出稿再写代码，期望 AI 调用设计工具 / 设计参考：「太丑了，你调用了mcp设计来吗？」（04-16）；「关于设置这一块，包括交互逻辑，全部调用 switch 的MCP重构出设计稿。完全不像话。」（04-16）；「从这边去找到最适合的design.md」（04-08，指 awesome-design-md）。
- 设计规则要写下来、长期复用：「然后把这个设计规范到时候一起写入这个skill里，确保以后我产出的调研报告都具备统一的设计风格。」（03-27 · mote-research）；「把你的这套排版规则记住。」（04-13 · 媒体采访提纲生成）；「定死这套规范。」（04-19）；「并且要把这个写入我根目录的claude.md里。」（03-31）。
- 写规则 / prompt 要高信息密度、定边界不定细节，不要越加越长（反复 3 次）：「整个prompt，你每次要加东西的时候，一定记住，是从更加宏观的规则去加，这个规则一定是信息密度极大的。一针见血的。」（04-08）；「这个优化必须是非常通用的，你不要一直往里面加各种规则。」（04-13）；「我不希望给你限定太死，因为规则是有上限的，我希望给你约束边界。所以需要极大的压缩信息密度」（04-14）。
- 提问要少字、给选项让 TA 用方向键选，并给推荐：「4. 如果你有不确定的信息就直接问我，但询问的文字不要太多。」（04-16）；「就是让我选择的时候怎么不是像别人的skill那边可以用上下左右的来选择。而是让我输入然后发送。」（04-16）。
- 讲解原理时做成带批注的 HTML 页，不贴代码（反复 3 次）：「把这些，弄成html网页，我要直观看，而且我没有代码基础，你要批注解释。」（04-13）；「可以给我整理一个HTML网页吗？就是他的回复逻辑是怎么样的。」（04-01）。
- 出错后不要辩解、不要写检讨，要说实话：「我都说了，不能继续用了，你还要给我讲嘴。」（03-26 · bitable-poster-generator）；「你可以自己看看，你又想写检讨了是吗？」（03-31 · new-bitable-poster-generator）；「我还是无法访问，我朋友也都无法访问，你为什么要骗人？」（03-30）；「你骗我，这两条都是你kb回的吧？」（04-13）。
- 用 TA 浏览器里的插件做真实浏览；遇登录墙就直接打开被改的那个页面：「用我claude 的mcp啊，你真的有那么蠢吗？我浏览器里不是有插件了吗」（04-08）；「那你可以换一种思路吗？就是打开对应的html。只针对你修改的那个网页去弄。」（04-16）。
- 用 TA 给的素材：「而且我发给你的那些图你都没用啊。每个论坛都有自己的主视觉啊」（04-16）。
- 「重构」=推倒重来，「调整」=局部微调，要分清：「不好看，重做，我说了。你要重构，你懂什么叫做重构吗？」（04-01 · callback-service）；「是所有组件啊这些，布局排版啊，你都要重构」（04-08）；对比「做好平衡，不是让你大改。」（04-17 · 议程生成）。
- 迭代变差就退回最早的版本：「你就按照一开始的方案吧。我觉得一开始那个还比较好。」（03-27 · mote-research）。
- 放权但要结果：「你看着办吧。总之要稳定能用」（04-14）；「我已经给了你最大的自由度。但是你并没有给予我应有的结果」（04-02 · 模板编辑器）。

## 演变（前后说法变了的）

- 主色蓝色：03-27「然后参考FBIF的蓝色。」、04-12「用白色的背景，主色调是蓝色。」→ 04-16 最终说法：「我的偏好不是蓝色，我只是这个项目是蓝色。」蓝色只是 FBIF 项目的品牌色，不是个人偏好。
- 调研报告页的导出：03-27 03:13 要 Word / PDF 按钮 → 03:40「右上角只保留一个share按钮」→ 05:33「然后这个页面不需要支持PDF和word的方式导出了。」→ 08:12 改成右上角「下载所有调研文件」按钮。方向：动作越收越少，收进一个入口。
- 引用角标：03-27 当天先改得更小、更花哨（「角标更丑了」），最后 TA 要求退回第一版（「你就按照一开始的方案吧」），最终要求带数字 + 「查看原文」按钮。
- 手机端议程：04-17 01:48「一切以手机端为准」→ 10 分钟后 01:58「不是，方向错了。」「做好平衡，不是让你大改。你的样式要跟PDF的保持几乎一致。」最终：只修溢出，版式和 PDF 一致。
- 议程交付形式：04-16「点击按钮应该进入一个html网页，然后顶部要做好设计和说明，右上角一个下载按钮。」→ 04-17「客户不需要再看到HTML页面了，相当于点击下载按钮之后，就直接下载PDF」。最终少一步。
- 公众号排版页的预览区：04-03 05:17 要求把封面提取出来放在预览旁边可改 → 同日 06:18「封面和标题，这一块不需要预览了。底部这一块也不需要预览了，看看简单点吧。」最终删掉。
- 折叠：多次说不要折叠（03-31、04-08、04-16、04-18），唯一一次要收起的是 04-13 自动识别出的列映射：「这个需要收起来。」，几分钟后改为「按钮就叫修改映射规则」「修改映射规则放在右上角」，数据预览也删了。最终：已自动完成的次要配置收进一个动作按钮，要读要改的内容全部展开。
- 转人工：03-27 不要「一进线就提示我转人工服务」→ 04-13「转人工的这个不应该自动弹出」「他就在kb的回答下，附上一个转人工的按钮。」。最终：不自动跳转，给按钮让用户选。

## 拿不准的（信号弱或可能是特定项目的需求，不该推广成通则的）

- 「人家都是用shift+鼠标滚轮」做缩放（04-02 · 模板编辑器）：主流画布工具通常是 Ctrl/⌘ + 滚轮缩放、Shift + 滚轮横向滚动（TA 04-13 也这样用 Shift + 滚轮横向滚动）。可以推广的是「照主流工具的手势」，具体键位不宜照抄。
- 调研报告用 DM Sans、配色参考 Claude 官网（03-27 · mote-research）：只针对这一类报告页。
