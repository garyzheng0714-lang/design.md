# 文字排版调研

`文字排版.md` 里每条规矩的出处和经过。

## 起因

2026-11-19 用户看完第一轮盲评：「所有设计的共性问题就是文字的处理及其差劲，文字是最考验布局功底的，换言之，如果能做好文字的布局排版，应该就解决了大部分的布局问题。」「应当参考业内的设计规范…我们站在巨人的肩膀上。关于文字的布局和排版设计，值得你花大量的时间进行调研。」

第一轮 9 份设计，首屏用了 4 到 8 种字号、7 到 18 种「字号+字重+颜色」组合，最乱的一份有 12.5、17 这种零碎字号和 8 种文字颜色。beUI 组件自己基本只用 14 和 12 两个字号、500 一种强调、深灰两层颜色。

## 实测：公认做得好的页面（2026-11-19 Chrome 实测首屏，字号/字重组合）
- linear.app/changelog：6 种组合、3 种文字颜色。
- developer.apple.com HIG Typography 页：5 种组合。
- github.com/vercel/next.js/issues：11 种（含顶栏、标签彩色胶囊）；列表每行只有两种：标题 16/500 主色，下一行 12/400 一种灰。状态只靠图标颜色。
- vercel.com/docs：11 种（含导航、侧栏）。
- Chrome 字重回退实测（只有常规和粗体的 Arial）：300/400/500 宽度相同 317.9，600/700/800 相同 331.2——500 显示成常规、600 显示成粗体，跟 Windows 微软雅黑同理。

## 国内设计系统的字体规范（2026-11-19 调研，sonnet 子智能体读官方 GitHub 源码）

### Ant Design【亲见 docs/spec/font.zh-CN.md 与 theme 源码】
- 字体栈不写中文字体（-apple-system … 'Noto Sans'），中文靠系统兜底；数字对比用 tabular-nums。
- 正文 14/22，主字号从 12 升到 14，依据 50cm 阅读距离。行高 = 字号 + 8。
- 标题 H1 38、H2 30、H3 24、H4 20、H5 16。
- 字重：多数情况只用 400 和 500，600 只在英文加粗时用。
- 原话：一个系统里字阶控制在 3 到 5 种；「避免毫无意义的使用大量字阶、颜色、字重强调视觉重点」。
- 文字颜色（黑色透明度）：88% 正文标题、65% 次要、45% 第三、25% 禁用。正文对背景 7:1 以上。

### Arco【亲见 global.less】
- 字体栈 Inter, -apple-system, BlinkMacSystemFont, PingFang SC, Hiragino Sans GB, noto sans, Microsoft YaHei …
- 正文 14，行高 1.5715。字阶 12/13/14/16/20/24/36/48/56。
- 文字颜色 4 层：#1d2129 / #4e5969 / #86909c / #c9cdd4（gray-10/8/6/4，映射未验证）。

### Semi【亲见 variables.scss】
- 字体栈 Inter, -apple-system, BlinkMacSystemFont, PingFang SC, Hiragino Sans GB, Microsoft YaHei, Segoe UI …
- 小 12、正文 14；标题 16/18/20/24/28/32。字重只定义 200/400/600。
- 文字颜色（#1c1f23 透明度）：100 / 80 / 62 / 35。

### TDesign【亲见 tdesign-common 源码；官网正文抓不到】
- 字体栈 PingFang SC, Microsoft YaHei, Arial；加粗用 font-family-medium（换字体族名，不用数字字重）。
- 网页：36/44、20/28、16/24、14/22（正文）、12/20；只有 5 级。移动端 10/12/14/16/18。
- 文字颜色：90 / 60 / 40（占位说明）/ 26（禁用）。

### 微信 WeUI【亲见 Tencent/weui 源码】
- 中文 PingFang SC, Hiragino Sans GB, Microsoft YaHei。
- cell 17px，提示 14px；文章正文 17/1.6，标题 22、20。
- 文字颜色：90 标题、55 描述、30 提示。

### 没拿到

### 共识
- 桌面正文 14、小字 12；手机（微信）正文 17、提示 14。
- 行高 字号+8 或 1.5。
- 字号 3–5 种（Ant 原话），TDesign 全套只有 5 级。
- 字重 400 + 500（Ant），600 不用于中文。
- 文字颜色 4 层：约 90 / 60 / 40 / 25 的黑色透明度。
- 没有一家正面写微软雅黑只有常规和粗两档怎么办。

## 排版手艺的经典原则（2026-11-19 调研，sonnet 子智能体）

- Butterick《Practical Typography》【亲见 summary-of-key-rules】：网页正文 15–25px；行距 120–145%；行长 45–90 字符；粗体斜体二选一、越少越好、不整段加粗；全大写只用于短文字并加 5–12% 字距。（按拉丁文写的，中文要换算）
- Bringhurst：单栏行长 45–75 字符，66 理想【转述，Wikipedia 引原书第 26 页】。
- Refactoring UI【章节标题亲见，正文 403 只能转述】：Size isn't everything；Don't use grey text on colored backgrounds；De-emphasize to emphasize；Labels are a last resort；Balance weight and contrast；Establish a type scale；Line-height is proportional。灰色备 8–10 档【亲见】。UI 不用低于 400 的字重【转述】。
- Material 2 强调层级 87/60/38%【亲见】。
- WCAG 2.2：正文 4.5:1，大字 3:1【亲见】。
- Linear 改版：标题用 Inter Display，正文 Inter；提高文字对比；主题变量从 98 个减到 3 个输入【亲见】。
- MDN：数字用 font-variant-numeric: tabular-nums，数字列右对齐；字体必须带 tnum【亲见】。
- MDN/Chrome：标题 text-wrap: balance（Chromium 最多 6 行），正文 pretty；line-clamp 标准写法 Limited availability，兜底 -webkit-line-clamp【亲见】。
- 没找到有出处的：「一屏最多几种字号」的具体数字、长标题截断还是换行。

## 中文排版的专门规矩（2026-11-19 调研，sonnet 子智能体）

### 字重
- 微软雅黑 / 雅黑 UI 只有 Light、Regular、Bold 三个文件【亲见 learn.microsoft.com/typography/font-list/microsoft-yahei】。
- CSS 字重匹配：目标 400–500 找不到时先往上到 500、再往下，所以 500 落到 400；目标 >500 先往上，所以 600 落到 700【亲见 MDN font-weight】。
- 苹方有 Ultralight、Thin、Light、Regular、Medium、Semibold，没有 Bold【转述】。所以 500 在 Mac 是中粗、在 Windows 是常规；600/700 在 Mac 是 Semibold、在 Windows 是 Bold。
- Ant Design 主张 400 + 500、600 只给英文——500 在雅黑上不生效，不能照抄。
- MDN：中日韩字体通常没有粗体斜体变体，建议对 zh/ja/ko 写 font-synthesis: none【亲见】。

### W3C clreq【亲见 w3.org/TR/clreq】
- 汉字、标点 1:1 方块无缝排；中西文之间最多 1/4 字宽，行首行尾不加（6.3.3）。
- 书籍行距为字高 50–100%（行高 1.5–2.0 倍），印刷数据，界面不直接套（7.1.1.5）。
- 书籍正文每行 17–40 字，横排不超过 48 字（7.1.1.5）。
- 省略号占两字宽；破折号不拆行。强调用黑体加粗或着重号，不提斜体。

### 文案排版指北【亲见 sparanoid/chinese-copywriting-guidelines】
- 中英文、中文与数字之间加空格；数字与单位加空格，° 和 % 不加；全角标点两侧不加空格；中文用全角标点，数字用半角；专有名词用官方大小写。

### CSS
- text-autospace：Baseline 2025，Chrome 140、Safari 18.4 起；Safari 默认可能是 no-autospace，要显式写 normal【MDN 亲见，版本转述】。程序拼出来的字符串仍要自己留空格。
- word-break: auto-phrase：只有 Chromium，实验性，不依赖。
- tabular-nums：Ant 建议纵向对比的数字使用【亲见】。

### 行高、字号下限
- Ant 14/22（约 1.57）；WeUI 正文 1.6。中文正文 1.5–1.6，字越大倍数越小。
- 中文不加字距：没有规范推荐（判断，无出处）。
- Lighthouse 以 12px 为参考线【转述】。雅黑 12px 在 125%/150% 缩放下是否发虚未实测。

### 最容易做错的 8 件事
1. 写 500/600 以为 Mac 和 Windows 一样。2. 用粗体做层级、粗体多了没重点。3. 没关 font-synthesis，伪粗糊成一团。4. 中文用斜体。5. 中英文、数字之间不留空格或全角标点旁多空格。6. 中文里用半角标点、数字写成全角。7. 小字号再配浅灰。8. 行高照搬英文 1.2–1.3，或标题正文同一倍数。另：Geist 后面不写中文字体，两系统各落各的。


## 第三轮前实测（2026-11-19，Claude in Chrome，用户的 Chrome 155 / macOS）

### 这台 Chrome 认不出系统字体名【亲见】
- 用户说 Linear 的前端、交互、深浅把控是顶尖水平，值得照着学。下面先记一个跟字体有关的发现。
- 在 `lang="zh-CN"` 的页面里，`sans-serif`、`-apple-system`、`system-ui`、`"PingFang SC"` 单独写或排在第一位时，中文和英文都显示成宋体和 Times。用画布逐像素比对，这几种写法的结果和 `serif` 完全一样。
- 只要第一位是一个真能加载的英文字体（自带的 Geist、Inter 网页字体，或者系统的 `"Helvetica Neue"`），英文就用这个字体，中文由系统补字，显示成苹方一类的黑体。
- 结论：字体栈第一位必须是能加载的英文字体，不能指望系统字体名。原因没查实，可能是 Chrome 的字体设置，也可能是新系统的问题。

### 第三轮的教训：不懂取舍（2026-11-19）
- 四栏对比页（同一份列表排四种字）被否：用户原话「不行，还是太乱了」「我看着头疼。」
- 改成一版「两行一条」：名字加一行灰字「发送中，已发送 152，失败 2」，字号压到 4 种。用户截图问：「你知道你最大的错误在哪里吗？」「你最大的错误是不懂取舍。」「你觉得linear会做出这种设计吗？」
- 错在哪：
  - 只学了 Linear 的字号和灰度数值，没学它的取舍。
  - 每行都重复「已发送」「失败」这些标签，状态图标表示过了，又用字说一遍。
  - 字号、颜色调得再准，字太多照样乱。
- 改法：列表一行一条，只留图标、名字、时间，数字挪进详情。见 iteration-3/one-line.html。

### 第四轮：接回软件、用 beUI 协调（2026-11-19）
- 用户看了一行一条的手写稿，说：「间距不对，布局风格的取舍，以及组件库我的规范，你都要做好协调」。
- 错在哪：手写的 HTML 脱离了软件本来的侧栏和两栏布局，也没用 beUI，间距是随手填的。
- 改法（iteration-3/send-records-desktop-list/S）：
  - 接回软件外壳：beUI 侧栏，加列表和详情两栏。
  - 间距一个用途一个值：
    - 字离栏边都是 24。
    - 标题行都是 56 高，三栏的第一行（侧栏第一项、列表标题、详情标题）落在同一条线上。
    - 列表一条 36 高。
    - 日期标签离上一组 20，离下面的行 6。
    - 详情里标题到状态 8，状态到数字 20，数字到日志筛选 12。
  - 状态图标统一成一套圆形（转圈、暂停圈、感叹圈、勾圈），颜色照 beUI 状态标签。详情里不用彩色胶囊，图标后面跟灰字。
  - 「继续发送」照项目规矩：别的表在发送时不显示，不摆点不了的按钮。
  - 数字用 500，不用 600：标签是灰的，颜色已经拉开了。
  - 自查：字号 4 种（12、14、16、20），字重 400、500、600，文字颜色只有主色和次色两层，外加失败数的红色。
- 侧栏账号的头像和导航图标同一列居中，名字和导航文字左边对齐（以前头像缩进了 10）。

## 状态不用字加颜色（2026-11-20）

- 起因：点对点工具的执行记录，每行写「已暂停」「已停止」「有失败」，还染成红色，计数写「已发送 12」「失败 1」。
- 用户原话：「这个红色看得我很不适」「我很讨厌文字，说实话」「用文字+颜色来展示状态是最愚蠢的一件事」。
- 改法：状态只留图标的形状（勾圈、暂停圈、叉圈、三角），要人处理的画深一档，状态名放进悬停提示。计数改成图标加数字（发送、叉、跳过），失败数也不染红。
- 这条替换了原来「只有要人处理的才用红色，只染图标或那个数字」。
- 同一天又被否：用户看了只剩图标的版本，问「你就一定想把这个状态呈现出来吗？」「你就不能是展开后用卡片的形式来呈现吗？」，状态图标和分组标题上的图标都问「这些是必要的吗？」；时间问「你就写 2026-11-20 15:05 这种格式的不行吗？」「最多加一个周几」。最后说：「我反复让你改了十几轮」「永远都是在做加法，而不是减法」。
- 定下的写法：列表一行只放名字和时间（2026-11-20 15:05），不标状态、不按状态分组；点开展开一张 beUI Card，状态、数字、原因和操作都在里面。验收加了「先做减法」一条。
- 又一轮：用户看到页顶的「执行记录」和重跑按钮，问「为什么你要重复搞个执行记录几个字？右边那个按钮是何意味？」「我查看执行记录不应该是支持搜素？」「我要那个按钮的意义？」「你到底懂我要干什么吗」。错在没先想用户打开这页要干什么：是找某一次发送。改成页顶放搜索框（按名字、表名、日期都能搜），去掉重复的页名和「重跑上次任务」按钮。验收那条「先做减法」前面加上「先写下用户打开这一页要做成什么事」。
