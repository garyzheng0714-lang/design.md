# 写真页面 → 用一遍 → 评审 → 交付

接着已有方案图做：先找齐 [mockup.md](mockup.md) 留下的功能清单、2.5 的六样（姿态、选中的骨架、形状、区域 → 组件、披露、因果）、方案图、评审结论，都在、和方案图对得上才往下；缺一样就回 mockup.md 补上那一步。写页面前从头到尾读过 [layout.md](layout.md)（先例关卡会核对）。

## 5. 照方案图写真页面

- 组件照 [rules.md](rules.md) 边界 4：每用一个组件先取它的文档（`node <本技能目录>/methods/heroui-react/scripts/get_component_docs.mjs <组件名…>`），照 [heroui-react](../methods/heroui-react/SKILL.md) 写：复合组件、`onPress`、语义变体；颜色只用 HeroUI 的主题变量类（`bg-surface`、`text-muted`、`bg-accent`……），不写色值，不改它的圆角和动效。HeroUI 没有的件照 [connect.md](connect.md) 拼或用成熟库。
- 分区、顺序、尺寸、交互和方案图一致；每块用 2.5 区域表里定的那个组件。写的时候发现方案图错了，回 mockup.md 第 3 步改了重审。
- 方案图是依据，不是代码来源：stageshow 的 kit、`Bar` 占位、写死的数据只留在 `design/` 里，真页面不引用。
- **因果和页面一起写，不留到最后**：2.5 因果表每一行都在这一步做出来（切换交叉淡入不留空、改值原位换字、插入让位、详情滑入），机制见 [motion.md](motion.md)。做完一行在页面上点一次看过渡。
- 照设计稿（Figma、截图）做：按 [build-design](../methods/build-design/SKILL.md)，只映射到项目那套组件和变量。
- 每块的加载、空、错误、长内容都要做出来，第 6 步在页面上逐个走到。

## 6. 用一遍、量一遍

- 在真实页面走完任务和失败路径（空、超长、出错、390 宽、收起态），浅色 / 深色都看。
- 截图：给 2.5 因果表每一行写一个场景，用 `node <本技能目录>/scripts/shoot.mjs <页面地址> --states <场景.json> --out <目录>` 拍（格式见脚本文件头；每个场景拍点后 90ms 和 700ms：90ms 那张取自录屏、要看得出正在过渡，停稳那张是结果；脚本同时报「点后 400ms 画了几帧」并写进 `frames.json`，≤ 1 帧就是一下子换好、没有过渡）。首屏 1440 与 390 默认就拍。
- 探针：`node <本技能目录>/scripts/probe.mjs <页面地址> --src <页面源码目录>`，对照 [layout.md](layout.md) §7 的预算；超了要么改，要么在汇报里写出这一屏为什么要多。
- 逐条过 layout.md §8 的坑和总纲 §2.3 的机器检查（一条不过就是致命）。
- 用户自己的十问（2026-07-10），每条答完：
  1. 第一眼能看出这个页面最重要的东西吗？
  2. 主操作是否足够明确？
  3. 字号层级是否超过 3–4 种？
  4. 间距是否来自统一 scale？
  5. 左右上下是否有清晰对齐线？
  6. hover / focus / disabled / loading / error 是否完整？
  7. 文案是否简洁、像人话？
  8. 页面在窄屏下是否仍然舒服？
  9. 长文本、空数据、极端数据是否会炸？
  10. 有没有为了好看牺牲可用性？
- 再答一句：「和先例比，我们哪一处不如它」，答不出就再看一遍图。

## 7. 评审找问题（校准前不报分）

另起没参与的智能体当评审；能起两个就用两个不同的模型，各评各的（没有子智能体就自己照做，汇报里注明「自评」）。只给它：总纲 DESIGN.md、功能清单、3 张先例、首屏截图（1440、390）、各场景的 90 / 700ms 截图和帧数、探针结果和页面源码；不给你的思路和方案说明。让它照总纲判、每条写证据（哪张图、哪个元素、哪行代码）：

- 致命：逐条过红线 1–14 和 §2.3 机器检查（探针报的列距、翻页也在里面），各判过 / 不过。
- 用户 11-07 打 40 分的那份错在哪（总纲 §2 的原话、§2.2 第三列）：这一页一条条犯没犯。
- 五项各 1–10，对照 §2.2「9 分的样子」：只用来找最弱的一项。
- 最该改的 3 处。

有致命、犯了那几处之一、或五项有一项 < 7：照评审意见改，再拍、再评（换新的评审，不给它上一轮的结论），最多三轮；三轮还过不了，停下把各轮评审报告和截图给用户看，写清卡在哪。AI 评审 11-07 把用户打 40 分的页面评成 75，校准（总纲 §2.4）之前分数不报给用户、不说「达到多少分」；85 分是技能要做到的水平，靠评测集和用户盲打分量（用户 11-07）。

## 交付

改后检查（插件钩子 `static-gate`）退回的问题都改掉。汇报写：先例 3 张（产品名 + Mobbin 链接）、2.5 的六样、方案图与评审结论、首屏和场景截图、探针对预算、各轮评审找到的问题和改了什么（不报分）、十问里答「否」的已改了什么。没走到的状态写「未验证」。
